xin.ng Build Sprint Plan
========================

Source document: xinng-linktree-clone-app-schema.md
Goal: Build the MVP first, then add monetization and advanced features later.

Core product idea
-----------------
xin.ng is a QR-powered Linktree-style app, but pages, links, and QR codes are separate product objects.

- Pages are page-builder surfaces. A page can contain many embedded links and QR code blocks.
- Links are standalone short links. Their main purpose is creating short, memorable, trackable URLs for teams, campaigns, and marketing. A standalone short link can also be added to one or more pages, and users can create a new short link while editing a page.
- QR codes are standalone trackable assets. A QR code can point to a page, a short link, or another supported destination, and can also be added to one or more pages.

The MVP can still start with one public page, page links, and one QR code, but the product model should not treat links or QR codes as only children of a page.

Recommended MVP stack
---------------------
- Backend: PHP 8+
- Database: MySQL or MariaDB
- Frontend: HTML, CSS, JavaScript
- UI framework: Bootstrap or Tailwind CSS
- Local environment: XAMPP
- Payments later: Paystack, Flutterwave, or Stripe

MVP database tables
-------------------
Build only these first:

1. users
2. pages
3. links
4. qr_codes
5. page_views
6. link_clicks
7. qr_scans

Do not build subscriptions, teams, custom domains, or advanced uploads until the MVP works end to end.

Sprint 0: Project Setup
-----------------------
Objective: Prepare the codebase, database, and app structure.

Tasks:
1. Confirm the app runs inside XAMPP at the expected local URL.
2. Create or confirm the MySQL database name.
3. Import the MVP database tables from the schema.
4. Confirm config.php connects to MySQL using PDO or mysqli.
5. Create shared helpers for:
   - Database connection
   - Session start
   - Auth guard
   - Redirects
   - Input escaping
   - CSRF token generation and validation
6. Create a basic folder structure:
   - assets/css
   - assets/js
   - uploads
   - includes
   - actions or controllers if needed
7. Add a simple app layout/header/footer if the project does not already have one.

Done when:
- The app loads locally.
- Database connection works.
- Shared helper files are ready.
- No database credentials are hardcoded into public pages except through config.php.

Sprint 1: Authentication
------------------------
Objective: Users can register, log in, and log out securely.

Tasks:
1. Build registration page.
2. Registration form fields:
   - Name
   - Email
   - Password
   - Confirm password
   - Optional page slug
3. Validate registration:
   - Name is required.
   - Email is valid and unique.
   - Password and confirm password match.
   - Password meets minimum length.
   - Slug is unique if provided.
4. Store password using PHP password_hash().
5. Generate a UUID for each user.
6. Create a default page after registration if the user provides a slug.
7. Build login page.
8. Validate login with password_verify().
9. Store user ID in session after login.
10. Update last_login_at after successful login.
11. Build logout action.
12. Protect dashboard routes from guests.

Done when:
- A user can register.
- A user can log in.
- A user can log out.
- Logged-out users cannot access dashboard pages.
- Duplicate emails cannot register.
- Passwords are never stored as plain text.

Sprint 2: Page Setup
--------------------
Objective: Users can create and edit their public xin.ng page.

Tasks:
1. Build dashboard page setup screen.
2. Page setup fields:
   - Page title
   - Bio
   - Page slug
   - SEO title
   - SEO description
   - Publish/unpublish status
3. Validate page slug:
   - Required
   - Unique
   - Lowercase
   - URL-safe characters only
   - Reserved words blocked, such as login, register, dashboard, admin, qr, l, u
4. Create page record if the user does not have one.
5. Update existing page record if it exists.
6. Show public page URL in dashboard:
   - Local development: local app URL
   - Production target: https://xin.ng/u/{slug}
7. Build public page route:
   - /u/{slug}
8. Public page should show:
   - Page title
   - Bio
   - Active links placeholder if no links exist
   - "powered by xin.ng" branding for MVP
9. Hide unpublished pages from public visitors.

Done when:
- A logged-in user can create a public page.
- A logged-in user can edit the page.
- Slugs are unique and URL-safe.
- /u/{slug} loads the correct public page.
- Unpublished pages do not display publicly.

Sprint 3: Short Link Manager
----------------------------
Objective: Users can create short memorable links and place them on their public page.

Tasks:
1. Build dashboard short link manager.
2. Add link form fields:
   - Link title
   - Link URL
   - Link type
   - Description
   - Position
   - Active/inactive status
3. Supported MVP link types:
   - url
   - whatsapp
   - email
   - phone
   - payment
   - social
4. Validate links:
   - Title is required.
   - URL or destination value is required.
   - URL format is valid for normal links.
   - MVP link placement belongs to the logged-in user's page.
5. Build edit short link action.
6. Build delete short link action.
7. Build activate/deactivate action for page placement.
8. Build reorder action for page placement.
9. Display active page link placements on public page ordered by position.
10. For public page link buttons, do not link directly to destination URLs.
11. Use click tracking route:
   - /l/{link_id}

Done when:
- User can create a short link.
- User can edit a short link.
- User can delete a short link.
- User can activate or deactivate a link placement on a page.
- Public page displays only active links.
- Public link buttons route through /l/{link_id}.

Sprint 4: Link Click Tracking
-----------------------------
Objective: Track link clicks before redirecting visitors.

Tasks:
1. Build /l/{link_id} route.
2. Find the link by ID.
3. Confirm the link is active.
4. Confirm the parent page is published.
5. Insert a row into link_clicks.
6. Increment links.click_count.
7. Capture basic analytics:
   - page_id
   - link_id
   - visitor_id if available
   - IP address
   - User agent
   - Referrer
   - Device type if simple detection exists
8. Redirect visitor to the original destination URL.
9. Handle missing or inactive links with a clean 404 page.

Done when:
- Clicking a public link records a click.
- Visitor is redirected to the correct destination.
- Inactive or missing links do not redirect.
- Dashboard can show total link clicks.

Sprint 5: QR Code System
------------------------
Objective: Generate standalone QR assets that track scans and can be attached to a page.

Tasks:
1. Create a dashboard QR page.
2. For MVP, generate or display a QR code for:
   - /qr/{slug}
3. Store QR details in qr_codes:
   - page_id
   - name
   - destination_url
   - qr_image_url if generated as a file
   - foreground/background colors if supported
4. Build /qr/{slug} route for the MVP page QR.
5. /qr/{slug} flow:
   - Find published page by slug.
   - Find active QR code for page.
   - Insert qr_scans record.
   - Increment qr_codes.scan_count.
   - Redirect to /u/{slug}.
6. Display QR preview in dashboard.
7. Display the trackable QR URL in dashboard.
8. Preserve the product model that QR codes are standalone assets, even if the MVP stores one QR against one page.

Implementation note:
- MVP can use an external QR image URL or a PHP QR library.
- The QR destination must be /qr/{slug}, not /u/{slug}.
- Future QR codes can target a page, a short link, or another supported destination.

Done when:
- Dashboard shows a QR code for the user's page.
- QR code points to /qr/{slug}.
- Visiting /qr/{slug} records a scan.
- Visitor is redirected to /u/{slug}.
- Updating page links does not change the QR route.
- Future QR codes can target a page, a short link, or another supported destination.

Sprint 6: Page View Tracking
----------------------------
Objective: Track public page visits.

Tasks:
1. On /u/{slug}, record a page view.
2. Insert into page_views:
   - page_id
   - visitor_id if available
   - IP address
   - User agent
   - Referrer
   - Device type if simple detection exists
   - Browser and OS if simple detection exists
3. Avoid tracking dashboard previews as public views.
4. Avoid storing unnecessary sensitive data.
5. Add simple duplicate-control if needed:
   - Optional: do not count repeat views from same visitor within a short time window.

Done when:
- Public page visits are recorded.
- Dashboard can show total page views.
- Dashboard preview does not inflate page views.

Sprint 7: Dashboard Analytics

Done when:

Sprint 10: MVP Security Pass
----------------------------
Objective: Tighten security before calling the MVP complete.

Tasks:
1. Confirm all passwords use password_hash().
2. Confirm login uses password_verify().
3. Add CSRF protection to forms that change data.
4. Escape all output with htmlspecialchars().
5. Validate all user input.
6. Confirm every dashboard action checks ownership.
7. Confirm users cannot edit/delete links or pages they do not own.
8. Confirm slugs cannot collide with reserved routes.
9. Confirm sessions are started consistently.
10. Use secure cookie settings where possible.
11. Validate uploaded files if uploads exist.
12. Hide raw database errors from public users.

Done when:
- No obvious cross-user access bugs exist.
- Forms have CSRF protection.
- Public output is escaped.
- App fails cleanly on invalid input.

Manual test flow:
1. Register a new account.
2. Log out.
3. Log back in.
4. Create or edit public page.
5. Add three links.
6. Deactivate one link.
7. Reorder links.
8. Visit /u/{slug}.
9. Confirm only active links display.
10. Click a public link.
11. Confirm /l/{link_id} records a click and redirects.
12. Visit /qr/{slug}.
13. Confirm QR scan records and redirects to /u/{slug}.
14. Refresh /u/{slug}.
15. Confirm page view count increases.
16. Return to dashboard.
17. Confirm dashboard analytics show:
   - Page views
   - QR scans
   - Link clicks

- Full flow works without manual database edits.
- A user can complete the MVP acceptance criteria from the Markdown spec.

Important Technical Rules
-------------------------
1. Pages, links, and QR codes are separate product objects.
2. Pages are page-builder surfaces.
3. Links are standalone short links for memorable, trackable URLs.
4. QR codes are standalone trackable assets.
5. Links and QR codes can be added to pages, and can also be created while editing a page.
6. QR codes must not point directly to their final destination.
7. MVP page QR codes must point to /qr/{slug}.
8. /qr/{slug} must record the scan, then redirect to /u/{slug}.
9. Public page link buttons must point to /l/{link_id}.
10. /l/{link_id} must record the click, then redirect to the final URL.
11. Passwords must use PHP password_hash().
12. Login must use PHP password_verify().
13. Public page slugs must be unique.
14. Dashboard actions must always check ownership.
15. Analytics should avoid storing unnecessary sensitive data.
16. Use xin.ng as the canonical production domain in public links, QR codes, and dashboard previews.
17. Keep MVP focused. Do not add payments, teams, or custom domains before the core QR/link flow works.
